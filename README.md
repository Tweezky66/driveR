# driveR

A monocular driver-assistance prototype exploring how far a single forward-facing
camera can go toward ADAS.

**Status: early-stage prototype (alpha), running on PC. Raspberry Pi deployment
is planned but not yet done - see Roadmap.**

## Architecture

```
driveR/
├── main.py                    # orchestrator - owns the loop, wires perception to visualization
├── calibration_tool.py        # one-time setup: click ground points, get a real homography
├── homography.npy             # generated by calibration_tool.py (not committed - camera-specific)
├── requirements.txt
├── assets/
│   └── icons/                 # top-down sprites (Kenney, CC0) for the HUD
├── perception/                 # "what am I looking at, and where is it really"
│   ├── Detector.py             #   pixels -> (class, confidence, bbox)
│   ├── BEVtransform.py         #   bbox -> real-world (x_lateral, z_forward) in meters
│   └── world_point.py          #   small vector type for future tracking/risk math
└── visualization/               # "how do I draw what perception figured out"
    ├── icon_map.py              #   class id -> sprite path
    └── HUD.py                   #   world coordinates -> pixels on screen
```

`perception/` has no idea a HUD exists - it only produces numbers.
`visualization/` has no idea YOLO exists - it only draws coordinates it's
given. `main.py` is the only file that imports both, because gluing them
together is its job.


## Known limitations (current, not aspirational)

- Distances are only as good as your calibration. Without a `homography.npy`,
  `main.py` falls back to an uncalibrated placeholder and prints a warning -
  don't trust distance numbers until you've run `calibration_tool.py`.
- No object tracking yet. Every frame's detections are independent - no
  persistent IDs, no real time-to-collision, just a static distance
  threshold for the warning color.
- Sign recognition is limited to COCO's "stop sign" class. No dedicated
  traffic-sign dataset fine-tuning yet.
- The ground-plane distance assumption breaks down for occluded object
  bases, sloped roads, or anything not touching the ground plane.
- Not yet deployed to or benchmarked on a Raspberry Pi - real-time
  performance on the actual target hardware is unverified.

## Setup

```bash
pip install -r requirements.txt
python main.py   # reads Datasets/test.mov by default
```

For a live webcam instead of a video file, point `cv2.VideoCapture` at `0`
in `main.py`.

## Calibrating for your camera

Ground-plane distance is only accurate once you've calibrated for your
specific camera mounting (height, tilt, field of view all affect this):

```bash
python calibration_tool.py path/to/calibration_frame.jpg
```

Click 4+ points on the ground plane whose real-world position you've
measured (lane lines, chalk marks, cone bases), enter each one's real
`(x_lateral, z_forward)` in meters when prompted. This saves
`homography.npy`, which `main.py` loads automatically on the next run.

## Roadmap

- [ ] `tracker.py` - persistent object IDs (Ultralytics' built-in
      ByteTrack/BoT-SORT rather than a from-scratch tracker)
- [ ] `risk_engine.py` - real time-to-collision from tracked distance deltas,
      replacing the current static distance threshold
- [ ] Traffic sign dataset fine-tuning (GTSDB or Mapillary Traffic Sign
      Dataset)
- [ ] Monocular depth estimation (pseudo-LiDAR style) as a richer
      complement to the ground-plane homography
- [ ] Raspberry Pi deployment - NCNN export, on-device benchmarking, camera
      and voice-alert integration

## Hardware target (planned, not yet built)

Raspberry Pi + camera module + small HUD screen + voice-alert speaker,
mounted on the windshield. See Roadmap - deployment hasn't started yet.
